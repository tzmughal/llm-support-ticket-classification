# LLM Fine-Tuning for Support Ticket Classification

Fine-tune DistilBERT end-to-end to route customer support tickets to the
right team: **Billing, Technical, Account, or Delivery**.

A support team that triages tickets by hand is slow and inconsistent. This
project shows the full loop a production ticket router needs: generate a
labelled dataset, fine-tune a transformer on it, compare it honestly against
a simple baseline, evaluate it, and ship a model that can be served,
monitored, and retrained.

> **Dataset is synthetic.** No real customer data is used. Tickets are
> generated from hand-written templates with randomised slots (see
> [Dataset](#dataset)).

## Results

Test set: **200 tickets** (50 per class), held out before training.

| Model | Accuracy | Macro-F1 | Weighted-F1 |
|---|---:|---:|---:|
| **DistilBERT, fine-tuned end-to-end** | **1.000** | **1.000** | **1.000** |
| TF-IDF + Logistic Regression (baseline) | 1.000 | 1.000 | 1.000 |

Per-class results, fine-tuned DistilBERT (test set):

| Class | Precision | Recall | F1 | Support |
|---|---:|---:|---:|---:|
| Account | 1.000 | 1.000 | 1.000 | 50 |
| Billing | 1.000 | 1.000 | 1.000 | 50 |
| Delivery | 1.000 | 1.000 | 1.000 | 50 |
| Technical | 1.000 | 1.000 | 1.000 | 50 |

![Confusion matrix, fine-tuned DistilBERT on the 200-ticket test set](screenshots/confusion_matrix.png)

**Read these numbers honestly.** The synthetic tickets are generated from
distinct templates per class, so the classes are highly separable — the
TF-IDF baseline already scores a perfect 1.000. The fine-tuned model does
not beat the baseline here, and 1.000 does not mean it would score 1.000 on
real tickets. What this run proves is the **end-to-end fine-tuning
pipeline**: the transformer trains, its loss falls, and it classifies
correctly. On real, messy tickets (typos, mixed language, multi-intent
messages) the transformer is the model expected to hold up better, but that
needs real labelled data to measure. See [Limitations](#limitations).

Training loss fell from **0.9454** (epoch 1) to **0.2172** (epoch 2).

## Dataset

- **1,000 tickets, 250 per class**, generated by `src/generate_data.py`
  (seed 42, fully reproducible).
- 20 hand-written templates per class, with randomised slots: order
  numbers (`ORD-10000`–`ORD-99999`), amounts (Rs 499–12,999), products,
  error codes, cities, and dates.
- Split (stratified, seed 42): **800 train / 200 test**, 200 / 50 per class
  in train / test.
- Files: `data/tickets.csv` (all 1,000), `data/train.csv`, `data/test.csv`.

Example tickets:

- Billing — *"I was charged twice for my order ORD-48210, please refund the
  duplicate payment of Rs 2499."*
- Technical — *"The app crashes every time I open the wireless headphones
  settings page, error code E417."*
- Account — *"I cannot log in to my account, it says my password is
  incorrect even after resetting it."*
- Delivery — *"My order ORD-73158 was supposed to arrive on Monday but it
  is still not delivered."*

## Method

**Fine-tuned model** — DistilBERT (`distilbert-base-uncased`), via Hugging
Face Transformers + PyTorch, trained in `src/train.py`:

- **End-to-end fine-tuning: all 66,956,548 parameters trained, no layers
  frozen.** The classifier head is randomly initialised and learned with
  the rest of the model.
- 2 epochs, batch size 16, learning rate 2e-5, max sequence length 64,
  AdamW, linear schedule with 10% warmup, gradient clipping at 1.0.
- Training time: **671.6 seconds** (~11 minutes) on CPU.
- The fine-tuned model is saved to `models/distilbert-support-ticket/`.

**Baseline** — TF-IDF (1–2 grams, 5,000 features) + Logistic Regression
(C=1.0, 1,000 iterations), scikit-learn. Included so the transformer is
judged against the simplest model that could solve the task, not against
nothing.

**Evaluation** — accuracy, macro/weighted F1, per-class precision/recall/F1,
and confusion matrix, computed on the held-out test set by
`src/evaluate.py`. All numbers in this README come from
[`results/metrics.json`](results/metrics.json).

## How to run

```bash
# 1. Install (CPU)
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt

# 2. Full pipeline: data, training, evaluation, confusion-matrix plot
bash run.sh

# 3. Classify one ticket
python src/predict.py --text "I was charged twice for my order" --topk 2
```

Individual steps:

```bash
python src/generate_data.py   # data/train.csv, data/test.csv
python src/train.py            # baseline + fine-tune, results/metrics.json
python src/evaluate.py         # re-evaluate saved model, screenshots/confusion_matrix.png
```

## Deployment, monitoring, and retraining

Deployment target: **Google Cloud Vertex AI**. This is the design for this
model; no live Vertex AI deployment was made in this project.

- **Deploy:** upload the fine-tuned model to Vertex AI Model Registry and
  serve it from a Vertex AI Endpoint, behind the ticket intake (form, email,
  or helpdesk API). Route by the top predicted label; send tickets below a
  confidence threshold (e.g. 0.60) to a human triage queue instead of
  auto-routing.
- **Monitor:** log every prediction with its label, confidence, and the
  eventual corrected label when an agent re-routes it. Track accuracy on
  human-reviewed tickets, per-class precision/recall, confidence
  distribution, and the share of low-confidence tickets over time. Alert on
  a sustained drop in any of these, or a spike in one class (often a real
  outage or billing incident, not a model bug).
- **Retrain:** collect corrected labels weekly, add them to the training
  set, and re-run `src/train.py` (same seed, same split protocol). Retrain
  on a schedule and on drift triggers: a new product, a new ticket type, or
  per-class F1 falling below its baseline. Version every model in the
  registry and keep the previous version live for rollback; only promote a
  retrained model after it beats the current one on the held-out test set.

## Model card

- **Model:** DistilBERT, fine-tuned for 4-class support-ticket
  classification. Base model: `distilbert-base-uncased`.
- **Training data:** 800 synthetic tickets (seed 42). No real customer
  data, no personal data.
- **Intended use:** routing support tickets to Billing, Technical, Account,
  or Delivery queues, with a human in the loop for low-confidence tickets.
- **Not intended for:** decisions about individual customers, refunds, or
  account closures — the model only suggests a queue.
- **Known issues:** trained only on clean, template-generated English.
  Performance on typos, Roman Urdu / mixed language, and multi-intent
  tickets is unmeasured.

## Limitations

- The dataset is synthetic and template-generated, so the classes are much
  more separable than real support tickets. Perfect test scores reflect the
  data, not a model that is perfect in production.
- 1,000 tickets is small. More data, and real tickets, would be needed
  before trusting the model without human review.
- No live deployment, A/B test, or latency measurement was done in this
  project; the Vertex AI notes above are a deployment design, not a
  deployed system.
- DistilBERT was chosen to keep training feasible on CPU (2 epochs,
  ~11 minutes). A larger model would likely need a GPU and more data to
  justify the cost.
